## ADR-0001: 숫자 판단은 코드, 글쓰기는 LLM

- 상태: Accepted
- 관련: `agent/specialists.py`(stage_checks), `config/rules.json`(thresholds)

### 배경
ESS 셀 온도 46°C가 경보 45°C를 넘었는지, SOC 86%가 상한 80%를 넘었는지 같은 판단은 틀리면 화재 위험으로 이어진다.
LLM은 크기 비교·비율 계산을 틀리거나 수치를 지어낼 수 있다.

> 2026-10-22 갱신: 기준값은 `status_criteria`(설비별 주의·경보)로 옮기고 판정은 `agent/diagnosis.py`가 한다 — ADR-0011.

### 결정
전문 에이전트의 assess 단계에서 계측값을 `config/rules.json`의 기준값과 **코드로** 비교해 이상 유형을 정한다.
LLM은 담당 단계 상황을 한 문장으로 요약하고 최종 보고서를 쓰는 데만 쓴다.

### 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| A. LLM이 계측값을 보고 이상 여부까지 판단 | 규칙을 안 써도 됨, 새 상황에 유연 | 비결정적, 46 vs 45 같은 비교를 틀릴 수 있음, 검증 불가 |
| **B. 코드가 판단, LLM은 글쓰기 (채택)** | 결정적·테스트 가능(pytest), 기준값 근거를 설명 가능 | 규칙에 없는 이상은 못 잡음 |
| C. 둘 다 하고 비교 | 교차 검증 | 비용 2배, 불일치 시 처리 규칙이 또 필요 |

### 결과 / 트레이드오프
- 판단이 단위 테스트로 고정된다(`tests/test_specialists.py`).
- 기준값이 [가정]이면 판단도 가정이다 → 기준값 근거를 별도로 채워야 한다.
- 규칙에 없는 새 이상(예: 인버터 과열)은 알람 키워드(`alert_keywords`)로만 잡힌다.

### 재검토 조건
실제 EMS의 이상 유형이 수십 개로 늘어 규칙 관리가 어려워지면, 규칙은 안전 이슈에만 남기고 나머지는 LLM 판단 + 코드 검증으로 전환을 검토.

## ADR-0002: 매뉴얼 선택 — RAG(MCP Tool) + 데이터 근거 가산점 + 안전 우선순위

- 상태: Accepted
- 관련: `agent/rag.py`, `agent/selection.py`, `mcp_server.py`(search_runbooks), 강의 ADR p.9(Retrieval을 Tool로)

### 배경
Base는 알람 문장에서 키워드를 목록 순서대로 찾아 매뉴얼 1개를 골랐다. ESS 1호기처럼 알람이 2개(충전 상한·과열)면
목록 앞의 "충전 상한"이 걸려 **화재 위험인 과열 매뉴얼이 빠졌고**, 연계점(피크·역송·DR)에서는 DR을 물어도 피크 매뉴얼이 나왔다.

### 결정
1. MCP Tool `search_runbooks`로 질문과 의미가 가까운 매뉴얼 점수를 받는다(검색은 Agent가 필요할 때 Tool로 호출 — 강의 ADR p.9의 B안).
2. 전문 에이전트가 데이터로 확인한 이상이면 +0.15 가산점(단, 의미 점수가 최소치 이상일 때만).
3. 1등이 기준 미만이면 질문이 애매하다고 보고 데이터로 확인된 이상 중 우선순위(안전 > 데이터 신뢰 > 계통 > 비용 > 효율) 1등.
4. 데이터로 확인된 안전 이슈가 주 매뉴얼과 다르면 함께 안내(최대 2개).

### 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| A. 키워드 순서 (Base) | 단순, 빠름 | 알람이 여러 개면 질문과 무관한 매뉴얼, 안전 이슈 누락 |
| B. 의미 검색만 | 질문 의도 반영 | "EV **충전**기"가 ESS 충전 상한으로 가는 단어 착시 |
| **C. 의미 + 데이터 근거 + 우선순위 (채택)** | 의도·데이터·안전을 모두 반영 | 기준값(min_score 등)이 임베딩 방식마다 달라 보정 필요 |
| D. 고정 RAG 파이프라인(매번 검색) | 구현 단순 | 잡담에도 검색 비용 |

### 결과 / 트레이드오프
- 주 매뉴얼 정답률 7/9 → 9/9, 안전 이슈 안내율 2/4 → 4/4 (fake 기준).
- 비용 +14%, MCP 호출 +37% (검색·전문 에이전트 요약).
- ollama·openai용 기준값은 가정값 — 실측 후 `rules.json`에서 보정해야 한다.

### 재검토 조건
매뉴얼이 수백 개로 늘거나(→ ADR-0007), 실모델 측정에서 의미 점수 분포가 기준값과 크게 다르면 기준을 재설정.

## ADR-0003: 사람 승인(HITL)은 설비 제어 조치에만

- 상태: Accepted
- 관련: `agent/approval.py`, `agent/graph.py`(approval_node, interrupt), `server.py`(/chat/resume), 강의 ADR p.18

### 배경
보고서에 "충전을 중지한다", "계통에서 분리한다" 같은 **설비를 실제로 움직이는 조치**가 들어간다. 이게 승인 없이 실행되면 사고로 이어진다.
한편 강의(ADR p.18)는 응답 품질 검수를 사람이 하는 안(D)을 "실시간성과 충돌, 매 응답 개입은 비현실적"이라며 기각했다.

### 결정
LangGraph `interrupt()`로 그래프를 멈추는 사람 승인은 **제어 조치가 있는 보고서에만** 건다(marker 또는 action_phrases로 판정).
응답 품질 검수는 사람 대신 코드 검사 + LLM 심판이 한다(ADR-0006).

### 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| A. 승인 없음 (Base) | 빠름 | 제어 조치가 그대로 나감(미승인 제어 문장 7건) |
| B. 모든 응답을 사람이 검수 | 가장 안전 | 실시간성 상실, 운영자 부담 — 강의가 기각한 안 |
| **C. 제어 조치에만 승인 (채택)** | 위험한 부분만 사람이 결정, 나머지는 자동 | 문구 기반 판정이라 다른 표현을 놓칠 수 있음 |

### 결과 / 트레이드오프
- 미승인 제어 조치 7건 → 0건.
- 판정이 문구 기반 → 표현이 달라지면 놓칠 수 있다. 조치를 JSON으로 구조화해 받는 것이 다음 단계.
- 승인 대기 상태를 저장해야 하므로 체크포인터가 필요하다(ADR-0005).

### 재검토 조건
실모델에서 승인 대상 누락이 측정되면 조치 문장을 구조화 출력(JSON)으로 바꾼다.

## ADR-0004: Error 격리 + 부분 보고(Partial Result)

- 상태: Accepted
- 관련: `agent/retry.py`(ToolError, with_retry), `agent/specialists.py`(collect), `agent/graph.py`(research·finalize), 강의 10장·12-4, ADR p.19

### 배경
설비 9대를 동시에 조회하는데, 그중 하나(예: EV 충전기 계측 서버)만 응답하지 않아도 예외가 `asyncio.gather` 밖으로 튀어
그래프 전체가 멈췄다. 사용자는 500 에러를 받고, 이미 받아 둔 다른 설비 데이터도 버려졌다.

### 결정
- 재시도는 일시 오류(timeout)만, 최대 2회, 0.5 → 1.5초 backoff. 그 외 오류와 재시도 소진은 `ToolError(code, user_message)`로 표준화.
- 실패는 **가장 작은 단위에서** 잡는다: 설비 1대 → 전문 에이전트 1개 → 매뉴얼 1개. 실패한 것만 `failed`로 기록하고 나머지는 계속.
- 최종 답변에는 코드가 "※ 일부 데이터를 받지 못했습니다: evc-01(TOOL_EXECUTION_ERROR)…"를 반드시 덧붙인다(LLM이 빠뜨려도).
- 의미 검색 Tool이 실패하면 데이터로 확인된 이상의 우선순위만으로 매뉴얼을 고른다.

### 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| A. Fail-fast (Base) | 단순 | 설비 하나 때문에 전체 실패 |
| B. try/except 후 로그만 | 응답은 나감 | 무엇이 빠졌는지 사용자가 모름 → 빠진 데이터를 정상으로 오해 |
| **C. 단위별 격리 + 실패 명시 (채택)** | 부분 정보라도 전달, 빠진 부분을 숨기지 않음 | 부분 데이터로 원인을 잘못 추정할 수 있음 |

### 결과 / 트레이드오프 (eval/run_scenarios.py S1)
- 장애 주입(evc-01 실패) 시 개선 전: `ConnectionError`로 응답 없음 → 개선 후: 답변 + 실패 설비 명시.
- 에너지 운영에서 "데이터가 없는 설비"는 그 자체가 위험 신호라, 숨기지 않고 "확인 불가"로 적게 했다.
- 공유 자원(MCP 서버 프로세스 자체)이 죽으면 결국 모든 조회가 개별적으로 실패한다 — 격리의 한계.
- 첫 조회 재시도 대기가 0.3 → 0.5초로 늘어 첫 질문 지연이 약 0.2초 늘었다.

### 재검토 조건
MCP 서버를 원격으로 분리하면(강의 ADR-0002 C안) 서킷 브레이커를 추가해 같은 서버에 반복 실패 요청을 보내지 않게 한다.

## ADR-0005: 체크포인터 — SQLite + 팩토리

- 상태: Accepted
- 관련: `agent/persistence.py`(create_checkpointer), `server.py`(lifespan), `agent/session_store.py`(pending_approvals), 강의 13장·ADR p.22

### 배경
승인 대기(interrupt)로 멈춘 그래프 상태가 `InMemorySaver`에만 있어서, 서버를 재시작하면 운영자가 [승인]을 눌러도 이어갈 상태가 없었다
(개선 전 측정: 재시작 후 resume → KeyError). 체크포인터를 `build_graph()` 안에서 직접 만들어 교체도 어려웠다.

### 결정
- `create_checkpointer()` 팩토리(`@asynccontextmanager`) 한 곳에서 저장소를 만들고, lifespan이 그래프에 주입한다. 그래프·테스트는 받기만 한다.
- 기본 SQLite(`checkpoints.db`), 테스트·측정은 `CHECKPOINTER=memory`.
- 승인 대기 목록(대화방 → 실행 ID)도 `session.db`에 저장. 끝난 실행의 체크포인트는 지운다(쌓이기만 하던 문제 해결).

### 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| A. InMemorySaver (개선 전) | 설치 불필요 | 재시작하면 승인 대기 소실 |
| B. PostgreSQL (강의 채택) | 재시작 내구성 + 여러 서버 인스턴스 공유 | DB 서버 설치·운영 필요 — 로컬 1대 운영엔 과함 |
| C. Redis | 빠름, 공유 가능 | LangGraph 지원이 상대적으로 제한적, 별도 서버 |
| **D. SQLite (채택)** | 파일 하나, 재시작 내구성 확보 | 파일 락 때문에 여러 인스턴스 공유가 구조적으로 어려움 |

### 결과 / 트레이드오프 (eval/run_scenarios.py S2)
- 재시작 후 승인 재개: 개선 전 실패(KeyError) → 개선 후 성공. 실제 서버 `kill -9` 후 재기동에서도 확인.
- 새 패키지 `langgraph-checkpoint-sqlite` 의존성이 생겼다.
- 단일 인스턴스 전제다.

### 재검토 조건
서버를 2대 이상으로 늘리거나 컨테이너로 배포해 파일을 공유하기 어려워지면 `persistence.py`에 `AsyncPostgresSaver` 분기를 추가한다(다른 파일은 수정 불필요).

## ADR-0006: 혼합 검수 — 코드 검사 + LLM 심판

- 상태: Accepted
- 관련: `agent/graph.py`(validate_node), `agent/validation.py`, `agent/fake_llm.py`·`ollama_llm.py`·`openai_llm.py`(judge), `prompts.py`(JUDGE_SYSTEM), 강의 9장·ADR p.18·p.21

### 배경
코드 검사(30자 이상, "1)" 포함, 수치 인용 확인)는 형식과 숫자는 잡지만 **의미 누락**은 못 잡는다.
"50자 이내로 짧게" 요청에 작성 모델이 그대로 따르면 안전 이슈(충전 상한) 조치가 빠진 답도 코드 검사를 통과한다.

### 결정
validate에서 코드 검사를 먼저 하고, 통과한 초안만 **작성 모델과 별개인 fast 모델**에게 4개 기준(Relevance / Completeness / Clarity /
Domain: 안전 이슈 우선·승인 표시)으로 판정시킨다. 불합격이면 심판의 reasoning을 피드백으로 재작성(최대 3회 시도 상한 유지).
심판 호출이 실패하면 코드 검사 결과만으로 진행한다. `rules.json`의 `validation.llm_judge`로 끌 수 있다.

### 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| A. 코드 검사만 (개선 전) | 결정적, 무료 | 의미 누락 못 잡음 |
| B. LLM 심판만 | 의미 판단 | 형식·숫자 같은 확실한 것까지 비결정적, 매번 비용 |
| **C. 코드 먼저 + 통과분만 심판 (채택)** | 확실한 건 코드, 애매한 건 심판. 심판 호출을 줄임 | 심판도 LLM이라 판정이 흔들릴 수 있음 |
| D. 사람 검수 | 정확 | 실시간성 상실 (ADR-0003 참고) |

### 결과 / 트레이드오프 (eval/run_scenarios.py S3, 회귀 세트)
- "짧게" 요청: 심판 끔 → 최종 답에 안전 매뉴얼 0/2개, 심판 켬 → 2/2개 (같은 코드에서 스위치만 바꿈).
- 그 문항 비용 $0.000344 → $0.001425 (재작성 1회 + 심판 호출). 회귀 10문항 전체 비용 $0.008233 → $0.008696 (+5.6%).
- fake 심판은 규칙으로 흉내 낸 것이라 실제 효과는 ollama/openai로 측정해야 한다.

### 실측 후 보정 (2026-10-21, OpenAI)
- 문제: gpt-4o-mini 심판이 **안전 이슈 매뉴얼이 없는 질문**(피크)에서도 일반 절차("ESS 방전 여유 확인")를 안전 이슈로 보고 3회 연속 반려
  → 재작성 상한에 걸려 통과. 기본 10문항 중 6문항이 3회 시도, 평균 검수 시도 2.3회(Ollama 1.5회).
- 보정 1 (지시문): 심판 입력에 "이번 보고서의 안전 이슈 매뉴얼: … / 없음"을 명시하고, 없으면 안전 우선 기준을 적용하지 말라고 지시
  → ESS 충전 상한 질문은 3회 → 2회로 개선, 피크 질문은 여전히 자기모순적 이유로 반려.
- 보정 2 (심판 모델): OpenAI 모드의 심판을 `OPENAI_JUDGE_MODEL`(기본 gpt-4o)로 분리 → 피크 질문 2회 모두 1회에 통과.
  심판 호출 단가는 오르지만, 오판 1번 = gpt-4o 재작성 1번이라 전체 비용은 오히려 줄어드는 방향(실측은 `실행_측정_기록.md`).
- 교훈: **심판이 작으면 "엄격함"이 아니라 "오판"이 늘고, 오판은 재작성 비용·지연으로 돌아온다.** 작성 모델과 "별개의 호출"이면 충분하고,
  반드시 "더 작은 모델"일 필요는 없다(강의 예시도 validator_llm을 별도로 둠).

### 재검토 조건

## ADR-0008: LLM 호출 전면 async + 동시 실행 상한

- 상태: Accepted
- 관련: `agent/ollama_llm.py`, `agent/openai_llm.py`, `agent/limits.py`, `agent/mcp_client.py`, `config/rules.json`(concurrency), 강의 12장 주의점

### 배경
- route/plan/analyze가 동기 `httpx.post`를 async 노드에서 불러, 실모델이 답하는 동안 **이벤트 루프 전체가 멈췄다**
  (다른 사용자 요청, SSE 토큰 전송, /health까지). fake 모드에서는 드러나지 않았다.
- 반대로 MCP 호출은 전역 `asyncio.Lock` 하나로 감싸 "병렬 조회"가 MCP 구간에서는 순차였다.

### 결정
- 모든 LLM 호출을 `httpx.AsyncClient` + `await`로 바꾼다.
- 대신 무제한 동시 실행을 막기 위해 상한을 둔다: LLM은 루프별 Semaphore(`llm_max_concurrent=2`), MCP는 서버별 Semaphore(`mcp_max_concurrent=4`).
  MCP ClientSession은 요청 id로 응답을 짝지으므로 동시 요청이 섞이지 않는다(27건 동시 조회 테스트로 확인).

### 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| A. 동기 호출 유지 (개선 전) | 코드 단순 | 이벤트 루프 블로킹 |
| B. `asyncio.to_thread`로 감싸기 | 변경 적음 | 스레드 풀 크기에 묶임, 취소·타임아웃 다루기 어려움 |
| **C. 전면 async + Semaphore 상한 (채택)** | 루프가 막히지 않음, 동시 수 제어 | 변경 범위가 넓음(LLM 3종 + 노드) |
| D. 전면 async, 상한 없음 | 최대 동시성 | 로컬 Ollama·API rate limit 과부하 |

### 결과 / 트레이드오프 (eval/run_scenarios.py S4, S5)
- 가짜 Ollama(호출당 0.5초)로 질문 2개 동시: 총 1.60초 → 1.06초, 이벤트 루프 최대 멈춤 1.05초 → 0.02초.
- MCP 27건 동시 조회: 0.061초 → 0.040초(로컬 stdio라 원래 빨라서 차이는 작음), 결과 섞임 없음.
- 상한값은 가정값 — 실제 Ollama 장비 성능에 맞춰 조정 필요.

### 재검토 조건
사용자가 늘어 상한에 자주 걸리면 큐 대기 시간을 메트릭으로 남기고 상한을 조정하거나 모델 서버를 늘린다.

## ADR-0009: 질문 3분류 — 잡담 / 설비 조회 / 이상 대응, 규칙 먼저

- 상태: Accepted (2026-10-22)
- 관련: `agent/intent.py`, `config/rules.json`(intent), `graph.py`(route, chat_answer, equipment)

### 배경
질문을 '잡담 / 이상' 두 가지로만 나눴더니 "확인 가능한 설비 종류 알려줘"는 잡담으로 가서 작은 모델이 "풍력·수력·지열"을 지어냈고,
"매뉴얼로 확인 가능한 내용은?"은 이상으로 가서 기본 설비(연계점) 진단을 내놓았다. 또 Ollama에서 "안녕" 한마디에 qwen3 생각 모드가 수 분간 돌아 멈춘 것처럼 보였다.

### 결정
1. 질문을 **잡담 / 설비 조회 / 이상 대응** 3가지로 나눈다.
2. **규칙을 먼저** 적용한다: 증상 단어가 있으면 이상 대응, 설비 목록·상태 요청이면 설비 조회, 인사·도움말·매뉴얼 목록이면 잡담. 규칙에 안 걸리는 질문만 AI가 분류한다.
3. 인사·도움말·매뉴얼 목록·설비 조회는 정답이 데이터에 있으므로 **AI 없이 코드가 답한다.**
4. Ollama 생각 모드(`think`)를 끄고, 잡담 답변은 0.6b 대신 8b가 맡는다(0.6b: "오늘 날씨는 흑색입니다").

### 대안
| 대안 | 기각 이유 |
|---|---|
| AI 분류만 (3클래스) | 작은 모델이 "잔량이 바닥이에요"를 설비 조회로 착각(실측) — 안전 질문을 놓칠 수 있음 |
| 잡담 답변 AI에 설비 목록만 넣기 | 지어내기는 줄지만 상태값까지 정확히 옮긴다는 보장이 없음 |

### 결과
"안녕" 0.0초, 설비 목록 0.1초(Ollama). fake 처음 보는 질문 6개의 판단 정확도 2/6 → 6/6(증상 단어 규칙).
대가: 증상 단어 목록을 관리해야 한다(새 표현이 나오면 추가).

## ADR-0010: 상황별 매뉴얼 — 절 단위 벡터화, 매뉴얼 선택과 상황 선택 분리

- 상태: Accepted (2026-10-22)
- 관련: `agent/rag.py`(split_runbook, RunbookIndex, runbook_excerpt), `data/runbooks/*.md`

### 배경
같은 이상(예: ESS 과열)이라도 원인(공조 고장·랙 편차·센서 오류·화재 징후)에 따라 대응이 완전히 다르다. 매뉴얼 1개 = 벡터 1개, 그것도 제목·증상만 벡터로 만들어 절차 본문은 검색에 쓰이지 않았다.

### 결정
1. 매뉴얼을 **기본 부분 + `## 상황 N` 절**로 쓰고, 절마다 벡터를 만든다(9종, 상황 38개).
2. **어떤 매뉴얼**인지는 기본 부분 점수(+ 데이터 근거 가산점)로 정한다. 상황 절은 키워드가 질문에 직접 있을 때만 매뉴얼 점수에 반영(+0.1).
3. **어떤 상황**인지는 ① 키워드(위쪽 상황 우선 — 위험한 상황을 위에) ② 의미 점수가 기본 부분보다 0.05 이상 높을 때 ③ 아니면 기본 절차.
4. 보고서에는 기본 부분 + **고른 상황 절만** 넘긴다. 상황마다 `대응:` 줄로 "기본 절차와 동일 / 기본 + 추가 / 기본 절차 대신"을 표시.

### 대안
| 대안 | 기각 이유 |
|---|---|
| 의미 검색만으로 상황 선택 | bge-m3에서 "타는 냄새" → 공조 고장 상황(화재 놓침) — 실측 |
| 상황 절 점수를 매뉴얼 선택에도 사용 | "EV **충전**기" 질문이 과열 매뉴얼의 "**충전** 중" 절에 끌려감 — 절이 많을수록 우연히 겹침 |
| 매뉴얼 전체를 보고서에 넘김 | 모델이 질문과 무관한 상황의 조치를 섞어 씀 |
| '적용 설비' 줄도 벡터에 포함 | "ESS 1호기"만 말해도 ESS 매뉴얼 점수가 함께 올라감 — 설비 ID는 표시용으로만 |

### 결과
상황마다 대표 질문 27개 → 전체 흐름(fake·TF-IDF)에서 매뉴얼+상황 27/27. 1차 검색만은 bge-m3 26/27.
대가: 매뉴얼 작성자가 키워드·순서 규칙을 지켜야 한다(`운영_가이드.md`).

## ADR-0011: 설비별 상태 판단 기준 — 계측값만 적고 상태·알람은 코드가 만든다

- 상태: Accepted (2026-10-22) — ADR-0001을 확장
- 관련: `agent/diagnosis.py`, `config/rules.json`(status_criteria), `mcp_server.py`, `data/monitoring.json`, `data/scenarios/full_incident.json`

### 배경
데이터 파일에 상태(`degraded`)와 알람 문장을 손으로 적어 두었다. 실제 운영은 계측값을 보고 문제를 **분석**하는 데서 시작해야 하고, '대응 요청' 버튼이 알람 문장을 그대로 복사해 "입력된 내용을 보여 주는 티"가 났다.

### 결정
1. 설비 종류(ID 앞부분)마다 판단 항목과 **주의·경보 기준**을 `status_criteria`에 둔다. 비율·여유 같은 파생값(연결률, 최대수요/계약전력, 전압 상승률, 상한·하한까지 여유)도 코드가 계산한다.
2. 경보 하나라도 있으면 **이상**, 주의만 있으면 **주의**, 아니면 **정상**. 보조 조건이 안 맞으면 **판정 보류**(예: 일사량 300W/m² 미만이면 발전 효율 판정 안 함).
3. MCP 서버가 조회할 때마다 이 기준으로 상태·알람을 만든다. 계측값으로 알 수 없는 외부 알림(EMS 스케줄 상충 등)은 `events`로 적는다.
4. 전문 에이전트 점검(`stage_checks`)·설비 조회 화면·설비 현황 패널이 **같은 기준**을 쓴다.
5. 시연 데이터(이상 4대)와 **테스트·평가용 고정 시나리오**(이상 8대)를 파일로 분리(`DER_MONITORING_FILE`).

### 대안
| 대안 | 기각 이유 |
|---|---|
| 계측값을 주기적으로 바꾸는 시뮬레이터 | 운영자 요청으로 제외 — 파일을 매번 새로 읽고 화면이 30초마다 새로고침하면 충분 |
| AI가 상태를 판정 | 숫자 비교는 코드가 확실(ADR-0001) |

### 결과
'대응 요청' 질문이 진단 결과로 만들어진다: "태양광 2호기(pv-02)에서 발전 효율 46% < 기준 60%, 전류 0A 스트링 1개 (전체 4개). 원인과 대응 방법을 알려주세요."
대가: 기준 숫자 대부분이 [가정] — 현장 기준으로 교체해야 한다.

## ADR-0012: 운영자 말과 데이터가 다를 때 — 확인부터, 단 직접 관찰한 위험 신호는 비상 대응

- 상태: Accepted (2026-10-22)
- 관련: `graph.py`(replan_check `data_confirmed`, research), `rag.py`(data_normal_situation), `prompts.py`, `fake_llm.py`

### 배경
시연 데이터에서 정상(31°C)인 ESS 1호기에 "온도가 계속 올라가요"라고 하면 과열 매뉴얼의 "충방전 즉시 중지"를 제안하고 승인을 요청했다.

### 결정
1. 질문으로 고른 매뉴얼의 이상이 전문 에이전트 점검(데이터)으로 확인되지 않으면 **데이터 미확인**으로 표시한다.
2. 미확인이면 설비를 움직이는 조치는 빼고, 판단 근거("셀 최고온도 31°C → 정상 [기준 …]")와 **현장·센서 확인 절차**를 안내한다. 매뉴얼에 `- 사용 조건: 데이터 정상` 상황이 있으면 그 절차를 쓴다(ESS 과열 → 온도 센서 오류 의심).
3. 단, 질문에 상황 **키워드**(연기·냄새·에어컨 꺼짐 등 운영자가 직접 본 것)가 있으면 데이터가 정상이어도 그 상황의 대응을 그대로 한다(화재 징후 → 대피·비상 정지).

### 결과
정상 설비에 대한 오경보로 설비를 멈추는 일을 막으면서, 센서가 못 잡는 화재 징후는 놓치지 않는다.

## ADR-0013: 승인 단계에서 운영자 수정 — 부분 승인·문구 수정·판단 반영 재분석

- 상태: Accepted (2026-10-22)
- 관련: `graph.py`(approval_node, `_effective_query`, `_after_approval`), `agent/approval.py`, `prompts.py`(OPERATOR_REWRITE_RULE), `server.py`(/chat/resume), `web_chat.html`

### 배경
승인/거부 두 가지뿐이라 "충전 중지 대신 출력 50% 제한" 같은 현장 판단을 넣을 방법이 없었다. 처음 만든 '판단 반영'은 보고서만 다시 쓰는 방식이라 문제 분석이 새로 되지 않았다.

### 결정
1. **부분 승인·문구 수정**: 조치별 체크박스와 문구 편집. 고친 문구는 "(운영자 수정)", 뺀 조치는 "(운영자 제외 — 시행하지 않음)"으로 보고서에 남는다(보고서에 없던 조치는 끼워 넣을 수 없음).
2. **판단 반영 = 재분석**: 판단을 적으면 그래프가 `approval → research`로 돌아가 ① 최신 계측값 재조회 ② 질문+판단으로 매뉴얼·상황 재선택 ③ 판단을 근거로 원인·조치 새로 작성 ④ 재검수 ⑤ 재승인. 판단은 누적되고 판단 속 숫자도 근거로 인정한다.
3. 판단 반영 지시는 **판단이 있을 때만** 작성 지시에 넣는다(항상 넣으면 Ollama가 없는 '운영자 판단 반영' 항목을 지어냄 — 실측).
4. 승인 대상 찾기를 넓힌다: 실모델이 "~하되, 운영자 승인 필요."처럼 표시를 다르게 쓰면 실제 제어 조치가 승인 목록에서 빠졌다(실측). 표시를 느슨하게 찾고 조치 표현을 추가. '운영자 판단 반영:' 요약 문장은 제외.

### 대안
| 대안 | 기각 이유 |
|---|---|
| 보고서만 다시 쓰기 | 운영자 판단에 따라 매뉴얼·상황이 바뀌어야 하는데(예: 스케줄 상충) 이전 분석에 묶임 |
| 운영자 수정 문구도 다시 검수 | 운영자 책임 영역 — 지금은 검수하지 않음(재검토 조건: 요청 시) |

### 결과
Ollama 실측: 판단 반영 후 매뉴얼 상황이 '두 ESS 스케줄 상충'으로 새로 선택되고 판단대로 조치 3건이 새로 작성(26초).
대가: 승인 대상을 넓게 잡아 계획 문장("충전 계획 수립")도 승인을 물을 수 있다.

### 3. 개선 제안 (der_ops_agent에 반영할 내용)

각 항목: **무엇을 / 어느 파일 / 결과물에서 달라지는 것 / Before·After 측정 / 트레이드오프(한계 항목용)**

#### ★ I-1. Error 격리 + Partial Result + 오류 표준화 (강의 10장, 12-4)
- **무엇을**
  - `agent/retry.py`: `ToolError(code, user_message)` 추가. timeout만 재시도(0.5초 시작 ×3 backoff, 최대 2회), 그 외 예외와 재시도 소진은 `TOOL_EXECUTION_ERROR` / `TOOL_TIMEOUT_AFTER_RETRY`로 변환.
  - `agent/specialists.py` collect: 설비 1대 조회 실패를 그 설비만 `failed`로 기록하고 나머지는 계속.
  - `agent/graph.py` research: 전문 에이전트 하나가 통째로 실패해도 다른 에이전트 결과는 유지. 이벤트 `TaskFailed` 추가.
  - `agent/prompts.py` write_facts + finalize: "gw-01 조회 실패(통신 오류) — 해당 설비는 판단에서 제외" 문구를 보고서에 포함.
  - `web_chat.html`: 실패한 설비를 진행 표시에 ⚠로 표시.
- **결과물 변화**: MCP 서버나 설비 하나가 죽어도 500 에러 대신 "확보된 정보 + 실패한 부분 명시" 보고서가 나옴. 에너지 운영에서 "데이터를 못 받은 설비"를 숨기지 않고 알려 주는 것 자체가 안전 기능.
- **측정**: 장애 주입 테스트(특정 설비 조회 시 예외 발생) — Before: 그래프 예외 / After: 부분 보고서 + 실패 설비 명시. pytest로 자동화.
- **트레이드오프**: 부분 데이터로 판단하면 원인 추정이 틀릴 수 있음 → 실패 설비가 있으면 보고서에 "판단 신뢰도 낮음" 경고를 붙이는 것으로 완화. 공유 자원(MCP 서버 자체)이 죽으면 결국 전부 실패(강의도 같은 한계 명시).

#### ★ I-2. 블로킹 LLM 호출 제거 (강의 12장 주의점)
- **무엇을**: `ollama_llm.py`, `openai_llm.py`의 route/plan/analyze를 `httpx.AsyncClient` 기반 `async def`로 바꾸고, `graph.py`·`specialists.py`·`fake_llm.py` 호출부를 `await`로 통일.

- **측정**: Ollama 모드에서 질문 2개 동시 요청 → 두 번째 요청의 첫 이벤트 도착 시간 Before/After. (fake 모드에선 차이가 없어서 실모델 측정이 필요)

#### ★ I-3. Checkpointer Factory + 영속 저장 (강의 13장)

#### ★ I-4. LLM-as-a-Judge 검수 추가 (강의 9장)
- **무엇을**
  - `agent/validation.py`에 `judge()` 추가: 질문·수집 사실·초안을 주고 4개 기준(Relevance / Completeness / Clarity / **Domain: 에너지 운영 관점, 안전 이슈를 먼저 다뤘는가**)으로 `is_acceptable + reasoning`을 받음.
  - 기존 코드 검사(형식, 수치 인용)는 그대로 먼저 돌리고, 통과한 초안만 judge에게 보냄(비용 절약). 불합격이면 reasoning을 피드백으로 재작성.
  - fake 백엔드용 결정론적 judge(예: 안전 매뉴얼이 있는데 권장 조치에 없으면 불합격)도 만들어 테스트 가능하게.
  - `config/rules.json`에 `validation.llm_judge: true/false` 스위치.
- **결과물 변화**: "50자 이내로 짧게 답해줘" 같은 요청에 안전 조치가 빠진 답이 나가지 않음.
- **측정**: 품질 저하 유도 문항을 testset에 추가 → Before 통과 / After 반려 후 재작성. 비용·지연 증가분도 같이 기록.
- **트레이드오프**: LLM 호출 1회 추가(비용·지연 증가), 심판도 LLM이라 판정이 흔들릴 수 있음 → 코드 검사를 먼저 두는 "혼합 검증"으로 완화(강의 ADR p.21과 같은 철학).

#### I-5. (선택) 연관 설비 재조사 — Dynamic Planning 강화 (강의 8장)
- **무엇을**: 전문 에이전트가 "통신 두절"이나 "전력 수지 불일치"를 찾았는데 게이트웨이(gw-01)를 아직 조사하지 않았다면, replan_check가 gw-01 조사 task를 1회 추가(상한 유지).
- **결과물 변화**: "EV 충전기 데이터가 안 들어와요"에 게이트웨이 결측률까지 근거로 들어감.
- **트레이드오프**: MCP 호출 증가. 규칙 기반이라 강의의 LLM 충분성 평가와는 다름(설명 필요).

#### ★ I-6. ADR 문서 (강의 1장)
- **무엇을**: ADR 문서에 강의 형식(배경 → 결정 → 대안 비교 → 결과/트레이드오프 → 재검토 조건)으로 6~8개 작성.
  - 0001 숫자 판단은 코드, 글쓰기는 LLM
  - 0002 매뉴얼 선택: 키워드 → RAG(MCP Tool) + 데이터 근거 가산점 + 안전 우선순위
  - 0003 사람 승인(HITL)은 "설비 제어 조치"에만 (강의는 응답 검수용 HITL을 기각 — 왜 우리는 범위를 좁혀 채택했는지)
  - 0004 Error 격리와 부분 보고 (I-1)
  - 0005 체크포인터 SQLite (I-3, Postgres 대안 비교)
  - 0006 혼합 검증: 코드 검사 + LLM 심판 (I-4)
  - 0007 벡터 DB 없이 메모리 임베딩 (매뉴얼 9개)
- **결과물 변화**: 발표의 "문제 → 개선 → 한계" 근거가 문서로 남음. 평가 항목 "한계·트레이드오프(20점)"에 직접 대응.
- **트레이드오프**: 없음(문서 작업). 코드와 내용이 어긋나지 않게 관리 필요.

#### I-7. SSE 정비 (강의 4·5장)
- **무엇을**: 스트리밍 응답에 `Cache-Control: no-cache`, `X-Accel-Buffering: no` 헤더 추가(간단). 선택으로 `POST /chat/stream` 추가 + `web_chat.html`을 강의의 Custom Transport 방식(fetch + `\n\n` 분리 + 미완성 조각 되돌리기)으로 교체.
- **결과물 변화**: 프록시 뒤에 배포해도 토큰이 실시간으로 옴. 질문 내용이 URL에 남지 않음.
- **트레이드오프**: POST 전환은 화면 코드 수정이 필요하고, EventSource의 자동 재연결 기능을 잃음.

#### I-8. MCP 품질 (강의 3장 주의점)
- **무엇을**: 세 Tool에 `ToolAnnotations(readOnlyHint=True, openWorldHint=False)`, docstring에 입력·반환·제약 명시. 매뉴얼 Resource 응답 끝에 `last_modified` 정보 포함(또는 별도 메타 Tool).
- **트레이드오프**: Resource 반환 형식을 바꾸면 읽는 쪽(`graph.py` read_runbook)도 함께 수정.

#### ★ I-9. thread_id 기본값·승인 대기 덮어쓰기 버그 수정 (강의 4-2)
- **무엇을**: `thread_id`가 없으면 서버가 `uuid4()`로 새로 만들어 응답에 돌려줌. 승인 대기 중 같은 대화방 새 질문은 안내 메시지로 막음(I-3과 함께).
- **결과물 변화**: API 사용자끼리 대화가 섞이지 않음.
- **트레이드오프**: thread_id를 안 보내던 클라이언트는 매번 새 대화가 됨(이름 기억 테스트는 thread_id를 보내야 함).

#### I-10. LangSmith Dataset 평가 연동 (강의 15-5)
- **무엇을**: `eval/testset.json`을 LangSmith Dataset으로 올리고 `client.evaluate()`로 실행. evaluator는 기존 지표(주 매뉴얼 정답, 안전 안내, 미승인 제어 0, 근거 없는 수치 0)를 heuristic으로, 선택으로 LLM 심판 1개.
- **결과물 변화**: Before/After 실험이 LangSmith 화면에서 나란히 비교됨(발표 캡처용).
- **트레이드오프**: **외부 서비스(LangSmith)에 테스트 질문을 업로드함** — `.env`의 키 필요, 업로드 전 확인 필요.

#### I-11. 동시성 상한 (강의 12장 주의점)
- **무엇을**: 전문 에이전트·MCP 호출에 `asyncio.Semaphore` 상한(rules.json 설정). `mcp_client.py`의 전역 Lock이 꼭 필요한지 확인 후 서버별 Lock으로 축소.
- **트레이드오프**: Lock을 줄이면 MCP SDK 동시 호출 안정성 확인 필요 → 측정 후 결정.

#### I-12. 구조화 로그 (강의 15-3)
- **무엇을**: 노드 실행·실패를 JSON 한 줄 로그로(`run_id`, `thread_id`, `node`, `elapsed_ms`, `error_code`) 남겨 LangSmith trace와 같은 ID로 연결.
- **트레이드오프**: 로그 양 증가. 이 규모에선 우선순위 낮음.
