## 2. 측정 도구 — 무엇을 재는가

### 2-1. 회귀 세트 측정 `eval/run_regression.py`
같은 질문 세트를 에이전트에 넣고 **답이 맞는지** 숫자로 셉니다. 승인 대기가 나오면 자동으로 승인해서 끝까지 진행합니다.

- 질문 세트
  - `eval/testset.json` (기본 10문항): 프로젝트를 만들며 함께 설계한 질문
  - `eval/testset_holdout.json` (처음 보는 6문항 H1~H6): 매뉴얼을 다 쓴 뒤 새로 만든 질문. **과적합 확인용**(규칙이 기본 질문에만 맞춰져 있지 않은지)

| 지표 | 뜻 | 좋은 방향 |
|---|---|---|
| 판단 정확도 (route) | 이상 질문/잡담 분류가 맞았나 | 높을수록 |
| 주 매뉴얼 정답률 | 질문 의도에 맞는 매뉴얼을 첫 번째로 골랐나 | 높을수록 |
| 안전 이슈 안내율 | 조회한 설비의 안전 이슈(ESS 과열·충전 상한) 매뉴얼을 모두 가져왔나 | 높을수록 |
| 미승인 제어 조치 | 운영자 승인 없이 나간 "설비를 움직이는 조치" 문장 수 | 0이어야 함 |
| 근거 없는 수치 | 최종 답의 숫자 중 질문·수집 자료 어디에도 없는 것 (지어낸 숫자) | 0이어야 함 |
| 평균 지연 | 질문 하나 처리 시간 | 낮을수록 |
| 비용 | 가상 단가 기준 합계 | 낮을수록 (트레이드오프로 해석) |
| MCP 호출 | 질문당 도구·문서 호출 횟수 | 많으면 비용·지연 증가 |
| 검수 시도 | 보고서를 몇 번 썼나 (1 = 한 번에 통과) | 낮을수록 |

### 2-2. 운영 시나리오 측정 `eval/run_scenarios.py`
"답이 맞는가"가 아니라 **장애·재시작·동시 사용 같은 운영 상황에서 버티는가**를 잽니다. 코드 폴더를 `--root`로 받아서 **개선 전 코드와 개선 후 코드에 똑같은 스크립트**를 돌릴 수 있게 만들었습니다(공정 비교).

| 시나리오 | 어떻게 재나 | 관련 개선 |
|---|---|---|
| S1 장애 주입 | EV 충전기(evc-01) 조회만 일부러 실패시키고 "EV 충전기 데이터가 안 들어오는 것 같아요" | I-1 |
| S2 재시작 후 승인 | 승인 대기에서 그래프·저장소를 새로 만든 뒤(= 서버 재시작) 승인 | I-3 |
| S3 품질 저하 요청 | "50자 이내로 짧게" 요청 → 최종 답에 안전 매뉴얼 2개가 남는가 (같은 코드에서 심판 끔/켬) | I-4 |
| S4 동시 요청 | 호출당 0.5초 걸리는 가짜 Ollama 서버로 질문 2개를 동시에 → 총 시간, 이벤트 루프 최대 멈춤 시간 | I-2 |
| S5 MCP 동시 조회 | 설비 27건 동시 조회 시간과 결과가 섞이지 않는지 | I-11 |
| S6 연관 설비 | "EV 충전기 데이터…" 질문에서 실제로 조사한 설비 목록 | I-5 |

"이벤트 루프 최대 멈춤"은 10ms마다 깨어나야 하는 작은 작업이 실제로 얼마나 늦게 깨어났는지입니다. 이 값이 크면 그동안 서버가 **다른 어떤 요청도 처리하지 못했다**는 뜻입니다.

### 2-3. LangSmith 실험 `eval/langsmith_eval.py`
기본 10문항을 LangSmith Dataset(`der-ops-agent-testset`)으로 올리고 `aevaluate()`로 실행합니다. 결과를 LangSmith 웹 화면에서 실험끼리 나란히 비교할 수 있습니다.

| 평가자 | 종류 | 점수 |
|---|---|---|
| route_ok, primary_runbook_ok | heuristic (결정적) | 0/1 |
| safety_coverage | heuristic | 0~1 |
| no_unapproved_action, no_uncited_number | heuristic | 0/1 |
| llm_judge | LLM 심판 (fast 모델, 4개 기준) | 0/1, 잡담은 제외 |

강의 ADR p.21의 "혼합 Evaluator"(결정적 heuristic + LLM 심판) 방식입니다.

### 2-4. 단위 테스트 `python3 -m pytest`
코드 조각이 의도대로 동작하는지 자동으로 확인합니다. 외부 서비스(LLM·인터넷) 없이 fake 모델과 실제 MCP 서버 프로세스로 돕니다.

**발견과 해석**

2. **처음 보는 질문의 약점은 매뉴얼 선택이 아니라 "조사할 설비 고르기"입니다.** 오답 4개 중 3개가 계획 단계에서 엉뚱한 설비를 조사한 경우입니다. 0.6b짜리 작은 계획 모델의 한계로, 다음 개선은 "질문에 직접 나온 설비는 코드가 항상 조사에 포함"입니다. 단, 이 6문항을 보고 고치면 과적합이 되므로 **새 질문 세트로 다시 검증**해야 합니다.
3. **근거 없는 수치 1건(1번)**: 검수가 지어낸 숫자를 잡아 반려했지만, 3번 다시 써도 고쳐지지 않아 "최대 시도 도달 → 통과"로 나갔습니다. 무한 재작성을 막는 상한의 대가입니다. 개선안: 상한 도달 시 답변에 "검수 미통과" 경고 표시.
4. **느립니다.** 질문당 평균 1~1.5분, 재작성 3번이면 3분. 지연의 가장 큰 원인은 검수 재작성이고, 운영에는 GPU 서버나 API 모델이 필요합니다.

2. **심판은 작을수록 싸지 않습니다.** gpt-4o-mini 심판의 오판 1번 = gpt-4o 재작성 1번. 심판을 gpt-4o로 올리자 **지연 43% 감소, 비용 17% 감소**. "엄격한 심판"이 아니라 "정확한 심판"이 필요함.

4. 남은 오답 2개(H1 설비 찾기, H4 DR 의미 검색)는 모델이 커도 남음 → 설비 별칭 보강과 매뉴얼 '증상 예시' 보강이 다음 과제(새 질문 세트로 검증해야 과적합이 아님).
