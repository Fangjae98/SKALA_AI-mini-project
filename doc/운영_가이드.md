# 운영 가이드 — 설비 데이터·상태 판단 기준·대응 매뉴얼

> 운영자가 직접 고치는 파일 3가지를 설명합니다. 바뀐 것이 어디에 반영되는지 먼저 보세요.

| 고칠 것 | 파일 | 반영 시점 |
|---|---|---|
| 설비 계측값 | `data/monitoring.json` | 다음 조회부터 바로 (패널은 30초마다 자동 새로고침) |
| 설비 추가·별칭(aliases) | `data/monitoring.json` | 에이전트 서버 재시작 후 |
| 상태 판단 기준(주의·경보) | `config/rules.json` → `status_criteria` | 에이전트 서버 재시작 후 |
| 대응 매뉴얼·상황 | `data/runbooks/*.md` | 에이전트 서버 재시작 후 (검색 벡터를 시작할 때 만듦) |
| 승인이 필요한 조치 표현 | `config/rules.json` → `approval.action_phrases` | 에이전트 서버 재시작 후 |

목차
- 1부. 설비별 상태 판단 기준
- 2부. 대응 매뉴얼 작성 양식

# 1부. 설비별 상태 판단 기준

> 기준 파일: `config/rules.json`의 `status_criteria` · 판정 코드: `agent/diagnosis.py`
> 숫자를 바꾸면 **서버 재시작 없이도** 다음 조회부터 반영됩니다(설비 현황 패널은 30초마다 자동 새로고침).
> [가정]이 붙은 값은 근거 없이 정한 값이므로 현장 기준으로 바꿔 주세요.

### 판정 방법

| 단계 | 내용 |
|---|---|
| ① 계측값 읽기 | `data/monitoring.json`을 조회할 때마다 새로 읽음 |
| ② 항목별 판정 | 정상 / **주의** / **경보** (보조 조건이 안 맞으면 '판정 보류') |
| ③ 설비 상태 | 경보가 하나라도 있으면 **이상**, 주의만 있으면 **주의**, 아니면 **정상** |
| ④ 문제점 분석 | 주의·경보 항목의 의미 + 의심되는 이상 유형(대응 매뉴얼) |
| ⑤ 대응 질문 | 문제 항목으로 '대응 요청' 질문을 자동으로 만듦 |

# 2부. 대응 매뉴얼 작성 양식

> 매뉴얼 파일: `data/runbooks/<이상 유형>.md` (9개)
> 완성된 예시: `data/runbooks/ess-overheat.md` (기본 절차 + 상황 6개)
> 수정 후에는 **서버를 재시작**해야 반영됩니다(시작할 때 검색용 벡터를 만들기 때문).

---

### 1. 한 파일의 구조

```markdown
## Runbook: <이상 이름> 대응 절차          ← 첫 줄 형식 유지. "어떤 매뉴얼이 있어?"에 이 이름이 나옴

- 단계: 저장                             ← 수집/생산/이동/저장/공급
- 적용 설비: ess-01, ess-02              ← 이 매뉴얼을 쓰는 설비 ID
- 적용: 언제 쓰는 매뉴얼인지 한 줄
- 증상 예시: 운영자가 실제로 할 말들     ← 매뉴얼을 고르는 검색에 쓰임. 많을수록 잘 찾음
- 기준(가정): 판단 숫자                  ← 근거가 없는 값은 (가정)이라고 적기

> 작성자 메모는 이렇게 > 로 시작하면 검색·보고서에 안 들어갑니다.

### 기본 절차                              ← 상황을 특정할 수 없을 때 쓰는 절차
1. 확인 단계
2. 설비를 움직이는 조치(운영자 승인 필요).
3. ...

### 상황 1: <가장 위험한 상황>             ← 위험한 상황일수록 위에!
- 키워드: 연기, 냄새, 가스                ← 질문에 이 단어가 있으면 무조건 이 상황
- 증상 예시: 운영자가 할 말들             ← 키워드가 없을 때 의미 검색에 쓰임
- 판단 근거: 어떤 값/신호로 이 상황이라고 보는지
- 대응: 아래 절차(기본 절차 대신)         ← 대응 방식 3가지 중 하나 (아래 2장)
1. ...
2. ...

### 상황 2: ...
```

---

### 2. "대응:" 줄 — 3가지 중 하나를 고르세요

| 쓰는 문구 | 의미 | 보고서에 들어가는 절차 |
|---|---|---|
| `- 대응: 기본 절차와 동일` | 기존 방법으로 똑같이 대처 | 기본 절차만 (상황 절에 번호 절차를 쓰지 않음) |
| `- 대응: 기본 절차 + 아래 추가 조치` | 기본 절차를 하고 추가로 더 할 일이 있음 | 기본 절차 + 상황 절차 |
| `- 대응: 아래 절차(기본 절차 대신)` | 이 상황은 완전히 다르게 대응 (예: 화재) | 상황 절차만 |

**판단 규칙**: "대신"이라는 단어가 있으면 기본 절차를 빼고, "기본 절차"라는 말이 있으면 넣습니다.

---

### 3. 상황은 어떻게 골라지나

```
질문: "ESS실에서 타는 냄새가 나요"
  ① 어떤 매뉴얼?  → 매뉴얼 '기본 부분'(제목·적용·증상 예시)과 질문의 의미 점수 + 데이터 근거
  ② 그 매뉴얼의 어떤 상황?
       - 상황 절의 키워드가 질문에 있나? → 있으면 그 상황 (위쪽 상황부터 확인)
       - 없으면, 상황 절 의미 점수가 기본 부분보다 확실히 높은가? (차이 0.05 이상)
       - 둘 다 아니면 → 상황 없음 = 기본 절차
  ③ 보고서에는 기본 부분 + 고른 상황 절만 넘김 (다른 상황 절은 안 넘김 → 엉뚱한 조치가 섞이지 않음)
```

- 질문에 원인 단서가 없으면("온도가 계속 올라가요") 특정 원인(공조 고장 등)을 **단정하지 않고** 기본 절차를 씁니다.
- 화면의 진행 단계에 `매뉴얼 선택: ess-overheat (상황: …)`로 어떤 상황이 골라졌는지 표시됩니다.

---

### 4. 잘 쓰는 요령

| 할 것 | 이유 |
|---|---|
| **위험한 상황을 위에** | 키워드가 여러 상황에 겹치면 위쪽 상황이 선택됨 (예: "타는 냄새 + 에어컨 꺼짐" → 화재) |
| **키워드는 짧고 분명하게** | "연기", "냄새"처럼. "온도"처럼 모든 상황에 나오는 단어는 키워드로 쓰지 말 것 |
| **증상 예시는 운영자 말투로** | "에어컨이 꺼짐", "한 랙만 뜨거움" — 실제로 칠 문장에 가까울수록 잘 찾음 |
| **설비를 움직이는 조치에는 `(운영자 승인 필요)`** | 승인 버튼은 문장 속 표현(충방전을 중지, 계통에서 분리, 출력 제한 …)으로 찾습니다. 새 표현을 쓰면 `config/rules.json`의 `approval.action_phrases`에도 추가 |
| **숫자는 근거와 함께** | 보고서에는 매뉴얼·계측값에 있는 숫자만 쓸 수 있음(검수가 지어낸 숫자를 반려). 매뉴얼에 적은 숫자는 그 상황이 골라졌을 때 보고서에 쓸 수 있음 |
| **파일 이름은 바꾸지 않기** | 파일 이름(`ess-overheat`)이 이상 유형 ID라서, 우선순위·안전 판단과 연결돼 있음 |
